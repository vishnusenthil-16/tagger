# Tagger implementation plan v4
Status: ACCEPT (v4), independently reviewed by anthropic/claude-opus-5.5 via OpenRouter on 2026-10-21. No implementation or runtime quality claims. All implementation gates remain open.

## Scope and architecture
Self-hosted stateless HTTP service; both hosted inference and fully local/private-network inference are required. One configured backend per deployment; same client contract. Python + FastAPI/Pydantic + httpx, pinned dependencies. No DB, queue, proxy, agent framework, presets, multi-label, UI or connectors.
Use one small /v1/systemone Choice transport where Jev and Laya compatibility is demonstrated. Provider-specific validation/token budgeting stays explicit rather than pretending wire compatibility gives semantic equivalence. No LiteLLM dependency initially: its real decision endpoints exist, but add no demonstrated benefit for this narrow two-endpoint deployment. No broad reuse study.
Jev hosted candidate; Laya local candidate. Before service construction, run a bounded compatibility/fitness spike on both. Laya is not an accepted default until input handling and quality gates pass. If it fails, evaluate one Ollama replacement and revise its adapter/score policy explicitly; no silent fallback or fine-tuning project.

## API and policy
POST /v1/classify: text plus ordered options [{id,description}], no client URLs, credentials, model or backend override.
IDs: unique ASCII [a-z][a-z0-9_-]{0,63}; 2–19 user options initially (20 including reserved __none__). Nonempty descriptions/text. IDs and descriptions are model-visible; document meaningful IDs and preserve request order. Email callers submit subject plus latest plain-text body, removing quoted history/signature deliberately; Tagger never silently strips content.
Inject __none__: "None of the supplied categories applies to this content." It is an evaluated hypothesis, not guaranteed OOD detection.
Service computes p_max and top-versus-runner-up gap from the validated raw distribution. One deployment policy names accept_min and margin_min, pinned model/revision and policy ID; no default thresholds. Thresholds fixed using tuning data only. Exact ties always needs_review. Else accept only if p_max >= accept_min and gap >= margin_min. Accepted __none__ => no_match, accepted caller ID => classified, otherwise needs_review.
Return status, label (null except classified), candidate (caller ID or reserved ID), complete provider-labeled raw distribution, separately named provider confidence if available, configured and backend-reported model identity, and policy ID. No claim that raw probabilities are calibrated or comparable across models. No recalibration in MVP. Tolerance must account for demonstrated response rounding and option count, not mask arbitrary malformed distributions; retain raw values without normalization.
Missing/extra labels, nonfinite/out-of-range probabilities, sum outside a backend-specific tolerance measured from actual response precision in spike B, or choice inconsistent with a maximum => backend_invalid_output; never repair silently. Threshold values bounded [0,1]; missing required config prevents readiness.
Thresholds are empirical for tested taxonomies/data distributions only. Each deployment has one intended taxonomy recorded with its tuning evidence, while API remains inline-options. Return policy applicability as evaluated only when option content/order hash matches the evaluated taxonomy; for other sets return needs_review plus candidate/scores (never automatic classified/no_match). Expose policy_applicability: evaluated|unevaluated. Document in API docs and README that generic unseen option sets produce review-marked suggestions until evaluated; this is an intentional conservative MVP product constraint. No preset CRUD/storage; deployment config carries evaluated taxonomy hash. This avoids exporting a threshold's claimed performance to arbitrary options. Changes require tuning/held-out evidence.

## Input, backend identity and deadlines
1 MiB HTTP body cap and explicit option/description byte caps; additionally per-backend budgets for fully assembled state, instructions, reserved option, option descriptions and special tokens. Local path uses pinned tokenizer and preprocessing identical to inference, with separate head/state caps and truncation disabled or detected/rejected. No rough character heuristic as proof. Reject excess before local inference. Hosted tokenizer, when unavailable, uses documented upstream limits and explicit upstream oversize errors; never promise precise local token rejection without tokenizer. Provider must reject rather than truncate; verify contract or fail integration gate.
Pin Jev concrete version (not latest/preview alias), Laya package/image and checkpoint/tokenizer revisions; explicitly select one checkpoint, disable routing. Record configured identity separately from actually reported identity; never fabricate missing provenance. Configure expected_reported_model explicitly (including legitimate routing names such as multilingual); if report conflicts, fail closed. Startup configuration plus mounted artifact verification supplies local revision provenance where API doesn't.
Use httpx directly with retries disabled, not a provider SDK with implicit retries. No automatic retries in MVP: one upstream attempt with absolute 30-second total deadline including admission, connection, response and validation; disconnect cancels waiting/upstream best-effort. Start with one in-flight call per process, no unbounded queue; overload 503. Document instant rejection of concurrent requests as the MVP behavior. Benchmark single-worker configuration before increasing concurrency.
Errors: invalid input 422; body too large 413; token/option limit 422; timeout 504; invalid upstream output 502; upstream failure 502/503 with sanitized code and retryable boolean. Service auth 401; upstream auth failures never masquerade as client auth failures. Upstream known token-limit 400 maps to 422; upstream 429/529 map to 503 with retryable=true. Tests cover upstream 400/401/422/429/529 and transport failures; no retry middleware.

## Deployment and privacy
Backend address and credentials only server-side. Hosted TLS verified. Both modes authenticate API clients for network exposure. Local inference on private internal network with its API key; not publicly published. Tagger may expose authenticated API ingress but local-mode service and inference containers have no external egress. Provision weights/tokenizers explicitly before runtime, pin mounts, set supported offline flags including HF_HUB_OFFLINE and TRANSFORMERS_OFFLINE; fail on missing artifacts. Do not use network=none where Tagger must reach a separate inference container. For container deployment use a declared internal Docker network and ingress arrangement that preserves both services' external-egress block; verify actual host/network behavior rather than assuming a published port or internal flag proves it. No cloud fallback. Log only timing, outcome/error codes and model/policy IDs; never text, descriptions, provider body or secrets, including exception logs.

## Sequence and acceptance gates
A. Record actual target hardware, representative email taxonomy, dataset splits and numeric targets BEFORE held-out runs. Provisional targets: accepted decision precision >=95% (including no_match), review rate <=30%, no_match precision >=90% and recall >=70%, warm p95 <=2s at concurrency 1 on recorded hardware, local total service+inference peak RSS <=8 GiB. Report sample counts and confidence intervals; these are screening targets, not guarantees. Evaluation must include clear, ambiguous, out-of-category, multilingual if in scope, instruction-like text, long-tail lengths, and misleading IDs. Compare accuracy/coverage to majority baseline at matching coverage. Split by thread/source to avoid leakage. No production-quality claims from tiny samples.
B. Compatibility/fitness spike: real hosted and local calls, pinned identities, reserved-option behavior, deterministic policy, cold/warm resource timing, per-stage input-budget checks and no truncation at boundaries. Explicitly test selecting one Laya checkpoint, disabling routing, actual reported model names, response precision, and choice behavior on ties. If laya-serve cannot safely expose/disable/detect preprocessing truncation, use the pinned Laya library in-process with its own tokenizer/assembly and a pre-truncation guard; this is a planned gate-B branch, not permission to silently truncate. In-process execution must remain bounded and keep capacity occupied until inference really stops even if the HTTP caller times out. Use tuning only to pick model/threshold; freeze before held-out. If an integration or quality gate fails, stop and revise it; no passing by weakening metrics after seeing test results.
C. Implement narrow service and mock contract/fault tests; live smoke calls confirm real adapter behavior. Test exact ties, malformed outputs, missing config, unknown taxonomy review, auth, overload, deadlines, disconnection and sanitized logs.
D. Reproducible hosted/local configurations. Prove fresh-container startup and classification with provisioned artifacts and blocked external egress; missing-artifact negative test fails closed without downloads. Verify unauthenticated local inference rejected, both services unable to call cloud, no input in logs, and near-limit inputs fully consumed.
E. Publish evidence locally: dataset/model/policy/config hashes, target hardware, counts, accuracy/coverage/no_match metrics, latency, resource use, and test results. Both deployment modes must pass before MVP complete. Gate failures can block runtime acceptance without invalidating an otherwise implementable design.

Design acceptance is authorization to proceed to these implementation gates, not proof they have passed.
